日期：2026-11-04。用途：供项目负责人、开发人员和架构审核者阅读。

数据库更新：S0 PostgreSQL 18.6 环境切换已完成，认证、UTF8 两空库、Windows TCP、
11 项离线测试、四服务探针、两库严格检查与中文临时 GIN 探针通过；旧 MySQL 已停并保留回退资源。
详细结果、测试覆盖凭据事件与剩余验证见[PostgreSQL 切换记录](myblog_PostgreSQL切换记录_2026-11-04.md)。
以下为设计及验收要求，不把旧 MySQL 结果当作 PostgreSQL 或业务并发验收。

这六项是在检查已确认功能怎样正确实现。后台用户与公开作者分开、全站共用媒体、
草稿不对外公开、历史文件不被误删，这些要求继续保留。
本轮已完成授权的服务切换、配置和探针，并完善设计与验收条件；业务开发、业务 schema 迁移或部署尚未开始。

## 先看推荐结论

| 审查项 | 推荐做法 | 目前还差什么 |
|---|---|---|
| 后台用户 | 最小 `identity.User`，公开作者另用 `Person` | 候选迁移及空库初始化验证 |
| 公共媒体模型 | 首次建表前采用最小自定义 Image、Document、Rendition | 确认模型路线，再验证后台兼容 |
| 多人审核 | PostgreSQL 条件唯一索引配合 Wagtail 工作流、统一事务和行锁 | 原生入口适配及真实 PostgreSQL 并发测试 |
| 正文与历史版本 | 每个 Revision 精确指向 MongoDB 的不可变内容版本 | 保存、发布和失败恢复测试 |
| 文件读取与删除 | 私有 RustFS、每次检查权限、完整引用保护、分步删除 | 逐个排查绕过入口并做故障测试 |
| AI 分工 | Sol 定方案、Flash 做常规实现、Terra 独立审查、Argon 处理框架难题 | 每次派发核对实际路由与完整结果 |

## 1. 后台用户：开始建表前确定

**目标。** 管理员和编辑用 `User` 登录；文章作者用 `Person` 展示。
作者可以没有后台账户，修改作者资料也不应改变登录权限。

**做法。** 推荐 `identity.User(AbstractUser)`，先沿用 Django 的账号、用户组和权限。
User 放在 `identity.0001_initial`，不反向依赖文章、作者或媒体，避免建表顺序循环。
现有首页迁移仍保留，不能因为增加 User 就删除、重跑旧迁移。

**怎么验证。** 获准编写候选迁移后，先离线检查依赖图；确认无环，再另行授权空库测试，
检查用户、首页、站点和权限是否正常创建。仓库有迁移文件，并不能证明数据库已经执行过它们。

**还没解决。** 当前没有 identity 模型和候选迁移，本轮没有连接数据库查询迁移历史。
若实际数据库已经按默认 User 建表，就要另做迁移方案，不能直接修改设置后运行。

## 2. 公共媒体：推荐最小自定义模型

**目标。** 一张图片可以同时被文章和教程使用；文档、音频、视频也都由全站统一管理。
Rendition 是原图按尺寸等规则生成的派生图片，例如缩略图。

| 选择 | 好处 | 需要承担的工作 |
|---|---|---|
| 原生 Image/Document，另加权限和引用表 | 框架模型维护少 | 扩展字段要另表关联，以后换模型要迁移已有数据 |
| 最小自定义 Image/Document/Rendition | 能直接放稳定资源标识等字段，适合从零建站 | 自管模型迁移、表单及升级兼容测试 |

**推荐第二种。** 继承 Wagtail 的 Abstract 基类（框架提供的模型扩展基础），
继续复用后台选择器、Collection（媒体集合）和图片处理；
不重写整个媒体系统。自定义 Rendition 指向自定义 Image，并保留框架要求的唯一约束。
Audio/Video 也放在公共媒体模块，不为 Blog 单建一套文件库。
两条路线都必须另做权限、历史引用和删除保护，自定义模型不会自动完成这些。

**怎么验证。** 检查模型设置和迁移图；之后测试上传、选择、重复生成缩略图、文档下载、
音视频播放及权限。当前还没有模型实现，不能称后台已经兼容。

**需要确认。** 编写模型前确认是否采用推荐路线；“全站共用媒体”本身无需重新决定。

## 3. 多人审核：冲突操作依次处理

**目标。** 两个人同时提交审核，不能产生两条有效审核流程；同时批准和拒绝，
也不能让已经过期的任务发布文章。

**发现。** 旧 MySQL 不支持 Wagtail 此处使用的条件唯一约束，曾产生 `models.W036` 警告。
PostgreSQL 支持对应的条件唯一索引，用于限制同一内容对象只能有一个“进行中或需修改”的工作流。
实际索引要在将来获准迁移后核验；索引本身不能保证批准版本正确或请求幂等。

**做法。** 首期推荐在 PostgreSQL 中设一条固定协调记录。后台相关变更先取得它的行锁，
相当于先排队；随后重新读取页面、任务和权限，再调用 Wagtail 原有工作流。
这条记录只管协调，不另存一套审核或发布状态。
代价是后台写入串行；先验证个人站的实际等待时间，有瓶颈再考虑按对象拆分。

提交、恢复、取消审核，批准、拒绝，直接发布和定时发布等入口都要接入。
旧任务请求拒绝；相同操作 ID 且输入摘要一致的重试返回原结果。
原生调用覆盖和锁顺序详见主方案 D1.1。
编辑后需要重新审批；最终发布时再核对获批版本与当前版本，不能让旧批准发布新草稿。
Wagtail 默认在审核结束时取最新版本发布，因此这项检查必须接入审核完成入口。

**怎么验证。** 用真实 PostgreSQL 的不同连接同时操作，检查重复审核、批准/拒绝冲突、
审批期间回收页面和重试。当前适配层及业务并发验证尚未完成；旧 W036 只作历史证据。
还要验证“V1 正在审批时保存 V2”，确保 V2 不能沿用 V1 的批准直接发布。

## 4. 正文与版本：读者看到完整的同一版

**目标。** 已发布 V1、新草稿 V2 并存时，访客继续看到 V1 的标题、日期、作者、封面和正文。
不能出现“旧标题配新正文”。

**做法。** Revision 是 Wagtail 保存的页面历史版本。每个 Revision 记录完整页面关系，
并指向 MongoDB 中明确的简介、正文版本；Mongo 旧内容不被覆盖。
正式页面按 Wagtail 的 `live/live_revision_id` 读取，不能取“最新正文”代替。
别名页面按主方案单独绑定源页面的正式版本，不能直接套用普通页面的读取方法。

| 出错位置 | 处理方式 |
|---|---|
| Mongo 保存结果不明 | 用原操作 ID 和摘要核对，再决定是否重试 |
| Mongo 已保存，PostgreSQL 失败 | 不发布；保留残留版本等待核对，不立即删除 |
| PostgreSQL 提交结果不明 | 按原操作 ID 查询结果；无法确定时提示“状态待确认” |
| 搜索或缓存更新失败 | 后台重试，读取时仍检查当前正式版本和权限 |

SQL 中的操作结果、Revision、引用记录和 Outbox 一起提交。
Outbox 是“与业务数据一起保存的待处理任务表”，用于补做搜索、缓存等工作；
它不决定文章是否发布。重复或过期任务不能覆盖新结果。

**怎么验证。** 检查保存草稿后所有公开字段仍为 V1，并注入超时、断连、
重复及乱序任务；再覆盖审批、排期、复制和历史恢复。当前没有做这些业务测试。

## 5. RustFS：能连接文件，不等于允许交付或删除

**目标。** 无权用户拿到文件地址也不能下载；仍有草稿、正式版、历史或回收站引用的文件不能物理删除。
RustFS 管理员身份不替代网站自身的权限规则。

**读取。** 桶保持私有，应用每次检查资源及对应页面访问权限后转发文件。
原图、缩略图、下载、预览、HEAD、Range 续传都要覆盖；首期不发可绕过即时检查的签名链接。
交付以响应提交前最后一次权限核对为准，缓存命中也要检查；权限改变后，新请求重新检查。
已经发送或在途的字节无法召回。

**引用。** SQL 记录哪个 Page、Revision、字段版本和内容位置使用了文件。
封面、图集、Markdown、表格、音视频和嵌套内容都要提取。索引不完整或不能确认时，拒绝删除。
替换文件生成新资源或文件版本及新对象 key，不能覆盖历史版本正在使用的文件。

**删除。** 先锁定资源、确认零引用，在 SQL 中标记“删除中”并记录任务；
新增引用和申请删除先取得同一协调锁，此后禁止引用“删除中”的资源。
后台再删除 RustFS 文件，核对成功后记录完成。
失败可以重试，不能先删文件再尝试回滚数据库；原生自动文件清理也要接管到此流程。
直接使用 RustFS 控制台或管理员 S3 操作会绕过应用保护，仍需人工核对和备份。

**怎么验证。** 同图被两种 Page 引用、只有历史引用、回收后仍有引用、删除时又新增引用、
篡改地址、未授权续传、文件删除超时，都必须有真实负例测试。当前未完成业务集成。

## 6. AI 分工：配置、运行和能力分开核对

分工保持不变：主会话拆任务并整合；Sol 负责架构；Flash 负责常规实现；
Terra 负责独立审查；Argon 处理框架疑难问题。参与高风险实现的代理不能担任同一变更的独立审查员。

本次已通过具名角色实际派发四类只读任务，并核对原生会话的模型选择记录。
具体任务、角色 ID、返回状态和限制见 [.codex/README.md](../.codex/README.md)。
这只能验证本轮角色调用及宿主选择的模型，不能单凭名称证明网关底层身份，也不代表后续编码能力已经验收。

每份任务写清目标、文件归属、允许操作和验收方法。路由不符或任务失败就如实报告，
不静默替换模型。共享文件由主会话整合，服务测试串行。
ai-memory 用于查历史决定和已知问题；当前任务走原生代理消息，不把记忆当授权或实时任务队列。

## 补充：首期支持中文全文搜索

输入“数据库”，应能找到正式文章标题、简介或正文中的内容；正文存放 MongoDB 也要能搜到。
推荐把正式 Revision 的可搜索文本同步到 PostgreSQL，由 Python `jieba==0.42.1` 分词，
再用 `simple` 配置生成 `tsvector` 并建立 GIN 倒排索引。搜索、Tag、栏目和 Archive
统一调用公共 `ContentQuery`，新增 Page 类型通过注册接入，公共模块不导入具体业务模型。
PostgreSQL 内置不自带中文分词，`simple` 本身也不会切中文词；索引与查询须使用同版本词典和归一化规则。
`pg_trgm` 可辅助子串/拼写匹配，不能替代分词；第二阶段 Elasticsearch 保留。
不要求读者自己给中文加空格，也不把 Mongo 原生 `$text` 当作中文全文方案。

草稿和回收站不能被搜出；列表、数量、统计、摘要和高亮都要检查当前发布版本及权限。
SEARCH-V2-FILTER 增补 A 原句、B 分词、C 受控同义词；推荐 A 命中即停止，
A 为零查 B，B 不足再按规则扩展 C，始终保留类型、Tag、栏目、日期和权限条件。
概念组之间 AND，组内备选词 OR；空关键词支持纯筛选，纯标点报错，不返回全部。
等级严格优先，再按相关度或所选日期排序；数据变化使旧游标失效，精确统计和8GB成本须实测。
详细推荐、冲突说明与验收见[统一搜索方案](myblog_统一搜索与组合筛选方案_SEARCH-V2-FILTER_2026-11-04.md)。
这补充原先未承诺的受控同义词，不代表提供语义搜索；临时 GIN 表只验证过基础中文、中英 AND 和单字 `LIKE`，
业务索引、正式 Revision、权限链、新排名及性能尚未验收。
