# myblog 上线前待办梳理与分步推进计划（2026-11-27）

> 本文面向正在学习 Django 与 Wagtail 的同学整理：用大白话讲清“还剩什么没做、为什么要做、每一步具体改哪里、做完怎么算通过”，方便后续按顺序一步一步解决。

---

## 先对齐一件事：Docker 文件怎么处理的？

仓库里原本有两类名字带 Docker 的文件，作用完全不同：

1. **用来把 Django 网站本身打包成容器的 `Dockerfile` 和 `.dockerignore`**：既然你确定用本机 Linux / WSL2 环境（Conda + Gunicorn/Nginx）直接启动网站，不用容器打包 Django，这两份文件**已按你的要求删除**。
2. **`infra/compose.yaml`（必须保留）**：它只负责启动背后的 4 个基础服务——**PostgreSQL 18（主数据库）、MongoDB 9（存文章正文积木）、RustFS（存图片和音视频文件）、Redis 8（缓存与验证码）**，和 Django 应用是不是 Docker 启动无关。

## 第一部分：上线前必须做完的 5 件事（P0，建议按顺序做）

> **P0 的意思**：不做完这些，公开上线后可能会出现**私密文章被外人看到、旧网站数据搬错、或者出了故障没法恢复**的风险。

### 第 1 步：堵住公开 API 和“推荐文章块”的权限漏洞

#### 这件事在说什么？（先搞懂背景）
- **PageViewRestriction（页面访问限制）**：Wagtail 允许站长给某个栏目或某篇文章设置“仅登录后可见 / 仅凭密码可见”。
- **祖先受限**：如果你给父栏目（例如“内部资料”）加了登录限制，那么它下面所有子文章虽然自己没单独设限制，也同样应该对外保密。
- **目前的代码漏洞在哪里？**
  1. **公开详情 JSON 接口**（`myblog/apps/api/views.py` 里的 `_serve_adapter_detail_api`）：现在是“先查 Redis 缓存；没命中就按 `slug` 和 `live=True` 直接从数据库读页面返回”。它没有检查：**这篇文章是不是属于当前访问的站点**、**文章自己或它的祖先栏目有没有设访问限制**，而且缓存键里也没带上站点和权限信息（一旦命中缓存，任何人都能读到缓存内容）。
  2. **公开列表 JSON 接口**（同一文件里的 `_serve_adapter_list_api`）和 **项目详情页里的“关联博客推荐”积木**（`myblog/apps/portfolio/blocks.py` 里的 `FeaturedPostsBlock`）：只检查了 `live=True`（已发布）和 `is_recycled=False`（没进回收站），同样忘了检查“父栏目有没有设访问限制”。

#### 目标、做法与验证
- **目标**：未登录的访客通过网页看不到受限文章时，通过 `/api/v1/...` 接口和推荐卡片也绝对拿不到它。
- **做法**：
  - 已在 `content_lifecycle/public_access.py` 统一收口 `get_public_blocked_path_prefixes`、`filter_public_page_queryset` 与 `filter_public_pages`（并由 `discovery/eligibility.py` 与 `discovery/query.py` 复用）；
  - 已收紧 `api/views.py`（严格按域名解析站点、同站重名 slug 防歧义、多维过滤与 `v2` 站级代次缓存键、`Cache-Control: private, no-store`）；
  - 已修复 `content_blocks/rendering/detail.py` 透传积木上下文、`CustomRichTextBlock` 公开页内链清洗、`FeaturedPostsBlock`（含搜索摘要防漏与 API `blocks.value` 过滤）以及 `GuidePage.related_guides` 过滤。
- **怎么验证**：已新增 `tests/test_p0_api_and_block_access.py`（3 组全量用例），并在 `test_myblog` 跑通相关共 60 项定向回归测试（见交付检查结果）。
- **还没解决什么**：当前 P0-1 代码与测试已在本地通过独立只读审查和回归测试，但仍在工作区未 `git commit` / 推送，`:8000` 与 `:8001` 服务尚未重启加载新代码，真机/浏览器尚未复查；历史已建有受限推荐文章的项目页如曾有旧索引摘要需按需重跑投影。

### 第 2 步：补齐旧站（`wagtailblog3`）搬家脚本的 3 道保险

#### 这件事在说什么？
- **ETL（抽取-转换-加载）**：就是我们写的 `scripts/migrate_from_wagtailblog3.py` 搬家工具，分三步把旧站数据从 `192.168.20.2` 导出、清洗格式、再写入新站 `myblog`。
- **目前缺了哪 3 道保险？**
  1. **旧站访问限制没搬过来，且导入后直接公开**：`remote_export.py` 导出旧站数据时没完整导出 `PageViewRestriction`，`loader.py` 导入文章后又直接调用 `.publish()`，可能导致旧站原本锁起来的文章搬过来后变成公开可读。
  2. **防写错库锁得不够死**：`loader.py` 里的目标库检查目前只硬拦了 `POSTGRES_DB == "myblog_dev"`。万一配置里把新数据库指向暂存库、却不小心配成了开发用的 Mongo 库或开发用的 RustFS 存储桶，还是可能串库写脏数据。
  3. **SSH 导出没校验主机指纹**：`remote_export.py` 连旧站服务器时跳过主机密钥校验，容易在网络异常时连错机器。

#### 目标、做法与验证
- **目标**：旧站搬家既不泄漏受限页面，也不可能误写开发库、开发 Mongo 或开发文件桶。
- **做法**：
  - 已在 `remote_export.py` 与 `migrate_from_wagtailblog3.py` 升级 v2 快照格式（含 `live`、`has_unpublished_changes`、`live_revision_id`、无口令 `page_view_restrictions` 元信息），强制读取已发布版本正文不回退草稿，启用 `StrictHostKeyChecking=yes` + `known_hosts` + `mktemp -d` 并移除 `--allow-dev`；
  - 已在 `loader.py` 落地三端成套目标隔离（PostgreSQL + MongoDB + `ProtectedRustFSStorage` 私有配置与成套命名锁定）、v1 旧快照与历史批次只读拦截、以及 `Pass 1 -> Pass 1.5 -> Pass 2` 严格发布顺序（无限制原公开页保持所有人可读，草稿/草稿祖先/未核准组映射/缺口令整支留草稿，已确认受限页先建限制后发布且媒体保持 `RESTRICTED`），并更新 `reconcile_target` 反向校验 `leaked_restricted_only_assets == 0`。
- **怎么验证**：已在 `tests/test_phase2_etl_migration.py` 覆盖公开保持公开、草稿/草稿祖先留草稿、受限媒体不泄漏、未核准组拦截、三端混库拦截、历史批次保护与 SSH 参数校验，并经独立只读审查通过。
- **还没解决什么**：当前 P0-2 改动仍在本地工作区未提交推送；尚未在授权后连接真实 `192.168.20.2` 重新导出 v2 快照并在 `.env.staging` 暂存环境实测。

### 第 4 步：收紧原生部署配置（不用 Docker，用 WSL2/Linux 直接跑）

#### 这件事在说什么？
- `myblog/wsgi.py` 是网站正式启动时的入口文件，现在第 22 行默认写着 `myblog.settings.dev`（开发配置）。开发配置会开着 `DEBUG=True`、允许任意主机访问，正式对外绝对不能这么用。
- 既然不用 Docker 启动网站，后面正式运行就是在本机 Linux / WSL2 里用 **Conda 环境 + Gunicorn（Python 应用服务器）+ Nginx（负责 HTTPS 和静态文件转发）**。

#### 目标、做法与验证
- **目标**：有一套干净的生产配置文件和启动命令，不暴露调试报错页、不把密码写进代码、静态文件一次打包就绪。
- **做法**：
  - 检查并收紧生产 `settings`（关闭 `DEBUG`、配置 `ALLOWED_HOSTS`、`SECRET_KEY` 从环境文件读取、安全 Cookie 头）；
  - 明确生产启动时通过环境变量 `DJANGO_SETTINGS_MODULE` 指定生产配置（避免依赖 `wsgi.py` 里的 `.dev` 默认值）；
  - 先执行 `python scripts/sync_vendor_assets.py check`，再执行 `python manage.py collectstatic --noinput`（把所有 CSS/JS 收拢到静态目录）；
  - 运行 Django 自带的生产安全体检命令：`python manage.py check --deploy`。
- **怎么验证**：`manage.py check --deploy` 无严重安全警告，Gunicorn 绑定本机回环地址（如 `127.0.0.1:8000`）能正常提供访问。
- **还没解决什么**：应用容器文件 `Dockerfile` 与 `.dockerignore` 已删除；原生生产配置与 `check --deploy` 待正式部署阶段补齐。

### 第 5 步：实测 Nginx 媒体代理（`X-Accel-Redirect` 和音视频拖动）与并发回归

#### 这件事在说什么？
- **Range 206 / 416**：你在网页看 MP4 或听 MP3 时拖进度条，浏览器会向服务器发“只要第 X 到 Y 字节”的请求。正常响应叫 `206 Partial Content`，位置越界叫 `416`。
- **`X-Accel-Redirect`**：开发时 Python 亲自把大视频字节流读出来发给浏览器，很占内存；正式上线时开启 `USE_X_ACCEL_REDIRECT=True`，Django 只负责“检查这个人有没有权限看”，检查通过后返回一个特殊响应头 `X-Accel-Redirect`，让旁边的 Nginx 直接去 RustFS 拉文件传给用户，既安全又省内存。

#### 目标、做法与验证
- **目标**：在真实 Nginx + HTTPS 环境下确认受限图片/文档/音视频权限不失效，大视频拖动进度条流畅且返回 `206`（越界返回 `416`）。
- **做法**：配置 Nginx 内部 `location /internal-rustfs/` 代理规则并实测；切流上线前再重跑一遍 PostgreSQL 真实并发回归测试。
- **怎么验证**：浏览器拖动长视频/音频进度条查看网络面板返回 `206`，未登录请求受限媒体返回 `403`。
- **还没解决什么**：目前只在开发模式（`USE_X_ACCEL_REDIRECT=False`）下测过，尚缺真实 Nginx 反向代理配置与实测。
