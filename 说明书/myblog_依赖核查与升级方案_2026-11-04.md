## 1. 目标和结论

先整理出新项目真正需要的依赖，再分组升级。你贴的 Conda 清单属于共享环境，
同时包含旧站、AI、数据分析和开发工具，不能直接当作 myblog 的安装清单。

建议采用以下顺序：

1. 先解决共享环境中旧站与新站的版本冲突，保留 Django 6.1 / Wagtail 8.1 路线。
2. 优先更新文件处理、HTML 渲染和网络访问相关的旧依赖。
3. RustFS 继续走 S3 协议，使用 boto3；接入 Django 文件字段时采用 django-storages。
4. 只在开发对应功能时加入 Markdown、缓存、测试和前端依赖。
5. 每组验证后生成可重复安装的锁定清单，再开始业务实现。

**原环境曾完成 MySQL 等基础服务探针，不能据此证明 PostgreSQL 通过，也不宜直接作为正式开发基线。**
`pip check` 实际退出码为 1，原因是 `wagtailblog2==0.1.0` 要求
`wagtail==8.0.1`，当前安装的是 8.1。最终复查仍失败，仅这一条冲突；升级新站并不能自动消除旧站的固定要求。

## 3. Python、框架和环境先怎么处理

### 3.1 保持框架路线，先更新补丁版本

| 项目 | 当前 | 本轮核对的候选 | 建议 |
|---|---|---|---|
| Python | 3.13.2 | 官方 3.13 分支已发布 3.13.18 | 保持 3.13 分支，准备环境时评估更新到 3.13.18；Conda 渠道是否提供该构建尚未核实 |
| Django | 6.1.2 | 6.1.3 | 优先做同分支补丁升级，保留 `<6.2` 上限 |
| Wagtail | 8.1 | 8.1 | 保持，不为了“更稳定”自行退回旧站版本 |
| Dockerfile Python | 3.14 | 尚未构建验证 | 实施前与 WSL 3.13 统一；不要同时升级 Python 主次版本和业务依赖 |
| Dockerfile Gunicorn | 写死 25.1.0 | PyPI 26.2.0 | 部署前单独评估，不在当前 WSL 文档核对中更改 |

Wagtail 8.1 官方兼容表包含 Django 6.1 和 Python 3.13，因此目前的框架组合有上游支持依据。
Python 3.14 也在支持表内，但本项目没有验证两种 Python 下的原生扩展和依赖结果完全相同。
Python 3.13.18 是官网已列出的版本，不代表当前 Conda 已升级到它。

### 3.2 共享环境冲突的处理建议

当前必须继续使用指定的 `wagtailblog-test`；本轮没有换环境或卸载旧站包。
正式实施前建议为 myblog 准备独立 Conda 环境，并在项目规则中确认新的解释器路径。
这样可以保留旧站环境，不必让一个环境同时满足 Wagtail 8.0.1 和 8.1。

如果继续共用现环境，需要另行明确旧站 editable 包的处理方式。
不能用忽略 `pip check`、降低 Wagtail、私改旧站依赖或直接卸载旧站包代替解决冲突。
也不能把环境中的全部包 `pip freeze` 后直接用作新站依赖。

## 6. 第一阶段功能需要哪些库

### 6.1 内容编辑和显示

建议复用 Wagtail 自带的 RichText、TableBlock、Chooser、人物关系和标签能力，
仅为需求中缺少的行为编写公共 Block。不要因为环境里已经有插件就绑定旧站实现。

| 能力 | 采用建议 | 版本 / 说明 |
|---|---|---|
| Markdown 渲染 | `Markdown` + `pymdown-extensions` | 候选 3.11.2 / 12.3；不再并行维护第二套 markdown-it 渲染协议 |
| HTML 清理 | `nh3` | 0.3.5 → 候选 0.3.7；按需求配置标签、属性、URL 协议白名单 |
| 代码高亮 | `Pygments` | 候选 2.21.0；只做展示，不增加代码执行沙箱 |
| 中文全文搜索 | Python jieba + PostgreSQL `simple` / `tsvector` / GIN，`pg_trgm` 辅助字面包含 | `jieba==0.42.1` 已列直接依赖；技术词保护、长文分块、A/B/C、排名与统计见统一搜索方案。`pg_trgm` 是数据库扩展，尚未启用；只索引正式 Revision |
| 语言、标签、树和关系 | Wagtail 配套包 | 随 Wagtail 范围锁定；见下一节 |
| Markdown 编辑器、数学、Mermaid、Lightbox | 前端 JS / CSS 依赖 | Conda 清单不能证明已经安装；当前无 package.json / 前端锁文件 |

数学公式、Mermaid 渲染和 Markdown 代码围栏不是装一个 Python 包就全部完成。
实施对应功能时，再选定 MathJax 或 KaTeX 中的一种、Mermaid 和一个图集显示库，
锁定 JS / CSS 版本与加载方式，并做后台预览和前台验收。
本轮没有查询 npm 最新版本，不能把未核对的前端版本写成安装结果。
Wagtail 自带表格编辑能力也不等于完整满足本项目 Markdown / Table 安全显示合同。

### 6.2 音视频

优先实现公共 Audio / Video 模型、文件选择和受控 Range 交付，
与公共 Image / Document 共用引用和权限检查。

`wagtailmedia` 当前 0.18.1、PyPI 稳定版 0.19.1，可以作为后续比较对象；
元数据接受 Wagtail ≥7 / Django ≥5.2，不等于已通过 Wagtail 8.1 的本项目验收。
不同时加入 `wagtail-video` 和多个媒体插件，避免出现不同的媒体身份、删除入口和权限规则。

当前 WSL PATH 未找到 `ffmpeg` / `ffprobe`。只上传并原样播放时不必先安装；
若要求读取时长、探测编码、生成视频封面或转码，应把它们列为系统工具，
另做安装、资源限制和失败处理。它们不是 pip 中的同名包装库。

### 6.3 缓存、任务、API 和搜索

- 缓存：先评估 Django 内置 `RedisCache` 加现有 `redis==8.1.0`，不必额外引入 django-redis。
  若需要其额外能力，再把已装 5.4.0 更新到候选 7.0.0 并测试序列化、TTL 和失效。
- Outbox 是与业务一起提交的 SQL 待处理任务表；首期使用专门管理命令处理。
  不因环境存在 Celery 就部署 worker，也不把 Redis 队列当作唯一任务记录。
  Celery 5.5.3 → 5.6.3 仅为后续候选，启用时需一起核对 Kombu / Billiard / AMQP；
  当前 Celery 对 Kombu 有上限，不能独立更新到 Kombu 最新版。
- `django-tasks`、`modelsearch`、`django-ninja`、DRF 是当前 Wagtail 的依赖，
  必须保留其兼容范围；安装这些库不等于开放 API v3 或另建公开 API。
- 第一阶段的正式搜索从正式 Revision 绑定的内容建立 PostgreSQL 查询副本。
  搜索、Tag、Archive 和栏目共用 `ContentQuery`，用 Python `jieba==0.42.1` 与技术词保护，
  再建 `simple` 配置的 `tsvector` 和 GIN；`pg_trgm` 辅助 A 原句字面包含，不替代中文分词。
  A/B/C、概念组 AND/组内 OR、受控同义词、DF/IDF、长文分块、排序统计及资源初值见
  [统一搜索方案](myblog_统一搜索与组合筛选方案_SEARCH-V2-FILTER_2026-11-04.md)，不新增搜索 pip 服务或改动本轮依赖。
  词典和查询协议须版本一致；技术词、标点、索引重建和短查询性能仍须验证。
  临时表探针不等于正式索引、权限和 Revision 集成验收；不得冒称已实现。
  `modelsearch` 不会自动索引外置 Mongo 正文，也不自动过滤所有业务权限。
- Elasticsearch、elasticsearch-dsl、elastic-transport 留到第二阶段。
  之后根据实际 ES 服务端、Wagtail 后端和官方客户端矩阵选择，不能直接从 8.x 升到 9.x。

## 8. 哪些包暂时不用，怎样管理

完整逐包归类见《第三方依赖清单》，这里只列项目边界：

- **不纳入新站当前依赖**：mysqlclient、mysql-connector-python、PyMySQL。
  Django PostgreSQL 驱动采用 `psycopg[binary]==3.3.7`；旧站共享环境中的 MySQL 包和系统库不卸载。
  MinIO SDK 已按前次明确授权卸载，RustFS 继续使用 boto3，不把这项历史卸载说成 MySQL 包也已卸载。
