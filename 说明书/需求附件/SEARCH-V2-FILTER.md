# myblog 搜索系统补充需求：统一公共查询、组合筛选与相关度算法

**需求编号：SEARCH-V2-FILTER**

**状态：产品需求已确认，技术实现方案待 Codex 完善**

**关联文档：myblog 全站中文搜索系统需求规格说明书（SEARCH-V2）**

**用途：作为 SEARCH-V2 的正式补充，要求 AI 重新完善整体搜索架构。**

---

## 一、核心架构原则：全站统一内容查询与搜索服务

### SEARCH-CORE-01：所有 Page 类型共用一套查询能力

**不为 BlogPage、GuidePage、Tag、归档等功能分别开发搜索系统，而是统一建设一套全站公共内容查询与搜索服务。**

这是本项目的强制架构原则，不是可选建议。

系统应以统一的公共查询服务（暂称 `ContentQuery`）为核心，为所有支持内容发现的 Page 类型提供一致的查询能力。

具体要求：

1. BlogPage、GuidePage 和未来增加的 XxPage 都通过公共接口接入。
2. 新增 Page 类型时，只需注册可搜索字段、可筛选字段、展示信息及必要适配逻辑，不应重新开发独立的全文搜索系统。
3. Tag 页面、栏目页面、年月归档、全站搜索页和内容列表都调用同一套公共查询能力。
4. 统一管理正式发布版本、访问权限、页面树范围、Tag、成文日期、搜索相关度和分页规则。
5. 不允许不同业务模块分别建立互不兼容的正文搜索索引、搜索权重、权限过滤和分页逻辑。
6. 允许各业务 Page 自定义展示模板、字段权重以及合法的业务筛选规则，但必须遵守公共查询协议。
7. 搜索索引、文本提取、搜索词处理和查询结果应具备统一的数据合同与版本管理机制。
8. 公共查询服务不能反向依赖 BlogPage、GuidePage 等具体业务 App；应通过注册与适配机制接入不同 Page 类型。

### SEARCH-CORE-02：搜索、筛选、归档属于同一套内容发现能力

从产品功能看：

- 全站搜索：按关键词查找内容。
- Tag 页面：按标签查看内容。
- 栏目页面：按 Page 树范围查看内容。
- 年月归档：按成文日期查看内容。
- Page 类型列表：按内容类型查看内容。

从架构看，它们都应该调用统一的 `ContentQuery`，只是查询条件和前端展示方式不同。

例如：

- 全站搜索：`关键词 + Page类型 + 日期`
- BlogIndexPage：`栏目后代 + BlogPage`
- 标签页：`Tag + 可选Page类型`
- 年月归档：`authored_on + 可选栏目`
- GuidePage 列表：`GuidePage + 其他筛选条件`

这些不是五套搜索引擎，而是同一套公共查询能力的不同使用方式。

**允许不同页面拥有自己的业务展示功能，但不允许重复建设底层查询系统。**

### SEARCH-CORE-03：统一服务不等于所有代码写在一个模块

Codex 可以根据职责拆分：

- 内容类型注册及适配。
- 正式发布文本提取。
- 搜索索引维护。
- 搜索词解析与中文分词。
- 结构化筛选。
- 相关度排序。
- 权限与正式版本校验。
- 结果展示数据组装。
- 归档分组与动态统计。

这些模块应通过共同接口协作，而不是分别建立独立的搜索体系。

技术方案需要明确公共 API、模块依赖方向及业务 Page 如何注册接入。

## 二、SEARCH-11：统一组合筛选能力

所有使用 `ContentQuery` 的页面均应支持按需组合以下条件：

| 条件 | 要求 |
|---|---|
| 关键词 | 完整原句、中文分词、同义词 |
| Page 类型 | BlogPage、GuidePage、其他注册的 XxPage，可多选 |
| 栏目 | 选择 Wagtail 页面树中的指定栏目 |
| 树范围 | 全部后代、仅直属子页面，按需包含栏目自身 |
| 指定 Page | 可限定单个 Page |
| Tag | 全站统一 Tag，可单选、多选 |
| 日期 | 按正式版本的 `authored_on` 过滤，支持年月及起止日期 |
| Site | 指定网站 |
| 权限 | 只能看到当前访问者有权访问且正式发布的内容 |
| 排序 | 相关度、成文日期等经过明确允许的排序 |
| 分页 | 稳定分页及正确结果数量 |

### 重要要求

Page 类型与 Page 树位置必须相互独立。

例如 BlogPage 可以出现在合法的 GuidePage 或其他业务 Page 下，不能假设 BlogPage 必须位于 BlogIndexPage 下。

任何业务页面都不能为了实现列表或归档而绕开公共权限与查询服务。

## 三、SEARCH-12：筛选和 A/B/C 搜索模式的统一执行规则

用户已经确认三种搜索模式：

- **模式 A：完整原句匹配，最高优先级。**
- **模式 B：中文分词和关键词关联搜索。**
- **模式 C：受控同义词扩展。**

这些模式必须与组合筛选协同工作。

### 统一搜索流程

1. 确定当前访问者能够读取的正式发布内容范围，排除回收站、未发布和不允许访问的内容。
2. 应用用户选择的 Page 类型、Site、栏目、Tag、成文日期等筛选条件。
3. 在有效候选范围内执行模式 A，查找完整原句。
4. 如果没有完整原句命中，进入模式 B。
5. 如果模式 B 的结果不足或用户明确要求扩大搜索，再考虑模式 C。
6. 对合法结果进行相关度排序、摘要生成、高亮和稳定分页。
7. 最终输出前校验正式发布 Revision、访问权限和结果一致性。

这是业务语义上的执行顺序，不要求 PostgreSQL 在物理执行计划中逐条顺序扫描。

Codex 应合理使用数据库索引、查询优化器、候选集和批量操作，避免把大量正文读取到 Python 内存中筛选。

### 强制规则

**A/B/C 搜索模式不得突破用户已经选择的筛选范围。**

例如：

用户输入“Django 数据库迁移”，选择：

- 2026 年
- BlogPage
- Python 教程栏目及全部后代
- Tag：Django

此时，只能在符合这些条件的已发布、可访问 Page 中搜索。

即使其他栏目中的 GuidePage 完整包含该句，也不能混入结果。

若符合筛选条件的内容中没有原句，才在相同筛选范围内执行分词搜索。

## 四、SEARCH-13：组合条件逻辑规则

### 1. 不同类型条件

默认采用 AND：

`关键词 AND 时间范围 AND Page类型 AND 栏目 AND Tag AND Site AND 权限`

### 2. 同一类型的多个选项

例如同时选择 BlogPage 与 GuidePage，默认采用 OR，即匹配其中任一 Page 类型。

### 3. 多 Tag 查询

应支持：

- ANY：满足任意一个选中 Tag。
- ALL：必须同时包含所有选中 Tag。

默认建议 ANY，技术方案应明确界面表现与 SQL 查询语义。

### 4. 成文日期

默认使用 `authored_on`，而不是 `first_published_at`。

日期来自当前正式发布 Revision 对应的业务版本，不得读取未发布草稿中修改后的日期。

起止日期按闭区间处理。

如果以后增加“发布时间”筛选，应作为独立条件定义，不能与成文日期混淆。

### 5. 没有输入关键词

必须支持纯筛选查询。

例如：

“显示 2026 年 Python 栏目下所有 BlogPage，按成文日期倒序。”

这种情况下不执行无意义的中文分词，也不强制要求用户输入关键词。

## 五、SEARCH-14：统一相关度排序算法

所有 Page 类型共用相同的基础搜索排序框架。

### 第一层：搜索模式优先级

1. 完整原句匹配。
2. 直接关键词匹配。
3. 同义词扩展匹配。

完整原句命中必须始终优先于普通关键词相关度结果。

不能只依赖一个较大的 boost 数值保证顺序。

### 第二层：同等级内部评分

需要综合考虑：

- 标题匹配。
- 简介匹配。
- 正文匹配。
- 专业术语命中。
- 重要关键词覆盖率。
- 词语距离和顺序。
- 词语区分度。
- 文章长度与词频。
- 必要的业务字段权重。

标题、简介、正文采用可配置的合理权重；默认标题通常高于正文。

不能让只匹配少量常见词的文章获得过高排名。

### 第三层：用户排序偏好

提供经过允许的排序方式，如：

- 相关度优先。
- 成文日期从新到旧。
- 成文日期从旧到新。

用户选择日期排序时，应明确它与搜索等级之间的优先关系，不得悄悄改变“原句优先”的默认语义。

时间、栏目、Tag 等筛选条件本身主要用于限制候选范围，不应该无理由增加文本相关度分数。

同分结果必须有稳定的次级排序规则，例如 Page ID。

### 特殊情况

短中文词、技术符号、版本号和特殊标识需要单独处理。

例如：

`C++`、`Django 6.1`、`Wagtail`、`WorkflowState`、`PostgreSQL 18`。

不能因为分词器丢失符号或拆分错误，就返回大量不相关结果。

## 六、SEARCH-15：统一分页、筛选统计和归档

### 公共结果结构

建议统一返回：

- Page ID
- 正式 Revision ID
- Page 类型
- 标题
- URL
- 成文日期
- 摘要与高亮信息
- 匹配模式与相关度
- 必要的 Tag、栏目或展示元数据

具体字段由 Codex 设计，确保所有业务 Page 可复用。

### 动态筛选统计

应支持按需要生成：

- Page 类型及其数量。
- Tag 及其数量。
- 栏目及后代数量。
- 年份、月份归档数量。
- 当前筛选条件下的总结果数。

统计必须遵守同一套访问权限、正式发布版本和筛选规则。

分页前后的数量应保持语义一致。

多维筛选统计是否忽略当前维度自身条件，Codex 应明确设计，避免出现统计值和结果列表无法解释的情况。

### 归档功能

Archive 应作为公共内容发现服务的消费者。

年月归档、栏目归档和按类型归档必须复用 `ContentQuery`。

不允许 Archive 另建一套绕开正式版本和权限检查的 Page 查询规则。

## 七、PostgreSQL 18 的技术设计方向

当前 PostgreSQL 已替代 MySQL，承担 Wagtail 关系数据及正式发布状态。

Codex 优先研究以下组合：

- `pg_trgm`：原句包含匹配及相关查询加速。
- Jieba：中文分词和技术词典。
- PostgreSQL `tsvector` 与 GIN：分词后的全文检索。
- `ts_rank` / `ts_rank_cd`：关键词相关度、字段与位置评分。
- B-tree 索引：日期、类型、站点和其他结构化条件。
- Page 树及 Tag 关系查询。
- PostgreSQL 查询计划和索引组合优化。

技术方案必须说明：

1. 如何建立全站公共 `PublishedSearchDocument` 或等效发布搜索副本。
2. 如何从 MongoDB 的正式 intro/body 字段版本提取可搜索文本。
3. 如何由 Wagtail 正式发布 Revision 决定索引内容。
4. 如何让新增的 XxPage 注册自己的索引字段。
5. 如何通过 Outbox 同步新增、更新、下架、回收、恢复及权限变化。
6. 如何避免重复事件、乱序事件和旧索引泄露草稿。
7. 如何构建完整原句索引、中文分词索引及稳定排序。
8. 如何在统一查询服务中完成栏目、Tag、日期、Page 类型和权限过滤。
9. 如何重建可丢失的搜索投影。
10. 如何控制 8GB 服务器的内存、CPU、磁盘和查询延迟。

搜索索引不能决定 Wagtail 页面是否发布。

MongoDB、Redis、搜索投影均不得取代 PostgreSQL/Wagtail 的正式发布权威。

## 八、架构禁止事项

以下情况不允许出现：

1. BlogPage 单独实现一套全文搜索，GuidePage 再复制一套。
2. Tag 页面和 Archive 页面各自建立不兼容的搜索索引与过滤代码。
3. 每新增一种 XxPage，就必须重新实现分词、权限过滤和分页。
4. 因为公共服务需要复用，就让公共查询模块直接依赖 BlogPage 的业务模型。
5. 使用 MongoDB 最新正文版本代替正式发布 Revision。
6. 为了方便搜索，直接把所有草稿和历史版本索引为公开内容。
7. 索引未同步时仍把已经下架、回收或受限的页面展示出来。
8. 因为有多个筛选条件，就把所有正文加载到 Python 内存里做全量遍历。
9. 为减少开发工作直接部署 Elasticsearch 或 mongot，而不评估 PostgreSQL 现有能力。
10. 为保证结果数量，降低相关度要求，强行返回不相关内容。

## 九、补充验收要求

Codex 至少设计以下测试：

1. BlogPage、GuidePage 和新注册 XxPage 能通过同一查询接口搜索。
2. Tag 页面、Archive 页面和栏目列表使用同一正式版本及权限规则。
3. 完整句子 + 特定年份。
4. 完整句子 + 指定 Page 类型。
5. 完整句子 + 栏目全部后代。
6. 仅直属子页面与全部后代范围差异。
7. 同时选择多个 Tag，验证 ANY 和 ALL。
8. Page 类型、Tag、日期、栏目同时筛选。
9. 原句只存在于当前筛选范围外，不能越界返回。
10. 当前筛选范围没有原句，自动进入分词搜索。
11. 不输入关键词，仅根据筛选条件显示结果。
12. 标题、简介、正文不同权重的排序。
13. 搜索常见词和专业词，验证不相关结果过滤。
14. 草稿修改日期、Tag、正文后，前台仍使用正式版本。
15. 下架、回收、权限变更后的结果、数量、摘要和高亮安全。
16. 分页稳定性、数据变更时的结果一致性。
17. 新增 Page 类型只需注册公共协议，不重复开发搜索系统。
18. 使用不同筛选组合测试 PostgreSQL 执行计划、响应延迟和内存峰值。

测试必须覆盖跨 Page 类型、跨栏目和跨存储场景。

请在现有 SEARCH-V2 的基础上，结合本补充需求重新完善全站搜索方案。

**首先明确并落实核心原则：统一公共内容查询与搜索服务，不为不同 Page 类型、Tag、栏目和归档分别开发搜索系统。**

请输出：

1. 全站内容发现总体架构及模块依赖图。
2. `ContentQuery` 公共接口设计与 Page 类型注册协议。
3. BlogPage、GuidePage、Tag、Archive 如何调用同一公共服务。
4. 原句优先、分词关联、同义词扩展的统一算法。
5. Page 类型、Tag、栏目、日期及权限组合过滤设计。
6. PostgreSQL 搜索索引、查询优化及相关度排序方案。
7. MongoDB 正文正式版本与 PostgreSQL 搜索投影同步方案。
8. 稳定分页、动态统计、归档与高亮数据合同。
9. 8GB 服务器下的资源预算及搜索质量验收方案。

**最终目标：建设一套可长期扩展的全站公共内容发现系统，既保持高质量中文搜索，也统一支持筛选、栏目、标签、归档和未来新增 XxPage，同时尽量控制 8GB 服务器的资源消耗。**
